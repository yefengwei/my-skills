# IT 业务模块梳理

针对一个具体的 IT 项目（同时包含前端与后端/微服务）中的某个业务模块，按用户给出的指示产出对应内容。支持两种模式，由用户在请求中明确以【梳理】或【生成】指定：

- **【梳理】**：聚焦核心，输出流程与骨架类内容（业务流程、前后端调用链路、状态流转、核心接口清单、数据模型概览、关键表结构），不展开逐行代码与冗长叙述。
- **【生成】**：产出完整、可交付的模块教程级 Markdown 文档，包含业务需求、实现分析、调用链路、数据表设计（SQL）、核心代码实现与总结，风格参照 `references/style-guide.md`，结构套用 `assets/module-template.md`。

撰写风格来源于「智学伴侣」**全量语料**（9 大类模块、82 个 .md、约 18.8 万行、9.3 MB，含 WMS / 神领物流 / 餐掌柜 / 智牛股 / AIGC / 秒杀 / 工作流 / 中州养老 / 云岚到家），以"业务驱动 + 实现落地"为主线：先讲清业务，再落到前后端实现，最后给出调用链路与代码。语料量化事实：Java 代码 1839 处绝对主导；图表为 0 处 mermaid、4677 张飞书截图（本环境统一改 mermaid，但保留"图必配文字解说"的习惯）；SQL 建表 156 处普遍带 COMMENT/InnoDB。

## 何时使用

- 用户给出形如「梳理一下 XXX 项目的 订单模块」「生成 XXX 系统 支付模块 的文档」「把 XXX 的 库存模块 整理成流程图和接口清单」的请求。
- 用户指定了"项目（含前后端）"与"某个模块"，并要求【梳理】或【生成】。
- 即便未显式写【梳理】/【生成】，若上下文能判定意图（如"整理成流程图"≈梳理，"写一份完整教程"≈生成），按最贴近的模式执行；拿不准时询问用户。

## 工作流程

### 1. 收集项目与模块上下文

在产出前，确认以下信息（缺失且无法从对话/代码推断时，主动用一次简短提问补全，不要臆造技术细节）：

- **项目背景**：项目名、所属业务域（电商 / 物流 / 仓储 / 金融 等）、核心目标用户。
- **技术栈**：前端框架（Vue/React/小程序…）、后端语言与框架（Java+SpringCloud / Go / Node…）、网关、中间件（MQ、Redis、ES…）、数据库。
- **前后端结构**：有哪些端（用户端 / 管理后台 / 司机端…）、有哪些后端服务/微服务、是否有 API 网关与鉴权层。
- **模块范围**：本次要处理的业务模块（如"秒杀""运费计算""入库管理"），及其边界（包含/不包含哪些子功能）。
- **模式**：【梳理】还是【生成】。
- **已有资料**：用户是否提供了需求文档、接口文档、表结构、现有代码路径。若有，优先基于真实资料产出，避免凭空编造字段与接口。

### 2. 拆解这个模块（两模式共用）

无论哪种模式，先把模块拆成统一视图，再按模式裁剪输出深度：

1. **业务流程**：模块在业务上怎么跑（参与者、步骤、分支/异常）。
2. **前端侧**：涉及哪些页面/入口、触发什么请求、关键交互与校验。
3. **后端侧**：涉及哪些服务/接口、职责划分。
4. **调用链路**：前端 → 网关 → 各后端服务 的串行/并行调用顺序（用 mermaid sequenceDiagram）。
5. **数据模型**：核心实体与表（用 mermaid ER 或 SQL `CREATE TABLE`）。
6. **核心规则/算法**：如运费计算、库存扣减、幂等、并发控制等。
7. **关键风险点**：高并发、分布式事务、一致性、超时、重试。

**选骨架**：根据项目性质决定顶层编号形式——
- **章节式**（`第一章 xxx` / `## 1、业务背景`）：体系化教程（WMS、餐掌柜、AIGC、秒杀、云岚到家、智牛股）。
- **日志式**（`# day03-运费微服务`）：按天/按课推进的实训笔记（物流、工作流、中州养老）。
两种骨架共用同一条主线（学习目标→业务→实现分析→数据→代码→总结），且同一篇内编号风格必须统一。

### 3. 按模式产出

- **【梳理】**：输出上述 1–5（偏重 业务流程图、调用链路图、状态流转、接口清单、表结构概览），用图表 + 短句，省略逐行代码与长篇讲解。目标是一页内能看清模块全貌。
- **【生成】**：严格套用 `assets/module-template.md` 的结构（二选一骨架），遵循 `references/style-guide.md` 的文风与排版，补全 SQL 与核心代码，产出完整文档。

### 4. 图表与代码规范

- **禁止依赖飞书截图**。原教程以嵌入截图承载架构图/流程图（语料中 4677 张截图、0 处 mermaid），本环境统一改用 **mermaid** 代码块：`flowchart`（业务流程/状态流转）、`sequenceDiagram`（调用链路）、`erDiagram`（数据模型）。
- **每张图必须配文字解说**：图前一句"下图展示…"、图后一句"由此可看出…"。原教程每张图都有长段图注，这是核心文风，不能丢；解说要落到结论而非空话。
- **代码块前必有引导句**（样本硬规律）：如"具体的代码如下：""xxx 表的 DDL 如下：""该 Service 中定义了 6 个方法…""POM 依赖："。代码块必须带语言标注（` ```java`、` ```sql`、` ```json` 等）。
- 需要表格时（接口参数、字段说明、技术栈对比）用 Markdown 表格。

### 5. 交付

- 将产出写入 Markdown 文件（默认在工作区创建 `<项目名>/<模块名>.md` 或按用户指定路径），并通过 present_files 交付。
- 若用户仅要在对话中查看，可直接输出，不落盘。
