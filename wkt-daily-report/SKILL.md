# WKT 日报填写 + 工作上下文沉淀

## 运行环境（必读，踩过的坑）

**必须用 WorkBuddy 内置 Python，系统 python 用不了：**

```
PY="C:/Users/ysq/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
```

- mise 的 `python` 在本机会报 `cannot find binary path`，不要用。
- 该环境已装 `openpyxl 3.1.5`（Python 3.13.14），读写 xlsx 正常。

  临时文件一律写到 `C:/Users/ysq/.workbuddy/skills/wkt-daily-report/.tmp/`（用 Write 工具写）。

## 跨 agent 工作上下文池（重要约定）

用户在多台会话/多个 agent 间轮换干活（主会话、子 agent、其他 AI 工具）。为了填日报时
不漏掉任何一处产出，本机维护一个「只追加、人机共写」的每日工作流水：

```
D:/yefengwei/wkt/公共盘/日报/context/YYYY-MM-DD.md
```

- **谁写**：任何 agent / 用户自己。某个 agent 干完活（或准备收尾）就追加一行，无论它是否
  负责填日报。
- **🔒 只记什么（用户 2026-09-03 明确）**：围绕 `D:/yefengwei/wkt` 的**软件开发**工作——
  业务模块开发 / bug 修复 / 联调测试 / 需求分析 / 技术评审 / 相关会议与文档，
  一行一条，含时间与来源：`- [17:20] [source: erp-be] 报价管理：完成包装运费计算接口`
- **🔒 一律不记（踩过实坑，2026-09-03 被用户清空重置）**：
  - agent 自身的工具搭建与维护 —— **包括本日报 skill 的开发与迭代本身**
    （解析模板、写脚本、修渲染问题只是"帮用户填日报"的手段，不是用户的工作产出）；
  - 环境配置、依赖安装、记忆/文档整理等 agent 内务；
  - 非公司事务（个人学习、课程、旅行、生活）。
  - 判断标准一句话：**这件事写进给主管的日报里，主管会认为"这是在开发公司系统"吗？**
- **格式**：纯 Markdown，追加行放文件末尾，**不改历史、不去重删改**。
- **用在哪**：生成日报时，它是与用户口头清单、git 提交并列的工作量素材池。

**沉淀动作（推荐每个 agent 收尾执行）：**

```bash
"$PY" scripts/log_ctx.py --source workbuddy-main \
    --msg "今天围绕 wkt 完成的 1~3 件开发工作，中文一句话一条"
# 长内容可走 stdin，多条用 \n 分隔；--tag 标注模块；--list 可回看
echo -e "完成 A\n完成 B" | "$PY" scripts/log_ctx.py --source erp-fe --msg -
```

- 无 `--date` 默认今天；`--date` 可补写昨天/前天的。
- 非 WorkBuddy 的 agent 不懂本 skill 也没关系：**它只需会追加文本到上述文件**即可接入。
- 用户自己的本地记事/IM 里零散记录当天做的事，也可让 agent 整理后追加进来。

## 模板结构（已解析，不要重新猜）

工作簿有 10 个 sheet：`Export Summary` / `Project Task List` / `Daily Work Schedule - SUN` /
`Monday`…`Saturday` / `Data Settings`。

日期公式链（**模板自带，一律不碰**）：

```
Data Settings!H1  = 本周一日期            ← 唯一允许写入的模板位置（初始化时设一次）
每个日 sheet E3   = 'Data Settings'!H1
每个日 sheet C5   = E3 + N   (N = 0..5，周一到周六)
G3                = 上班开始时间（模板 9:00，不许改）
I3 / I4           = "60 MIN" / =--LEFT(I3,3)（模板值，不许改）
B6                = G3
B7…               = B6 + TIME(0,'Daily Work Schedule - SUN'!$I$5,0)   ← 模板自带，不许动
```

> 🔒 **硬规则（用户 2026-09-03 明确）：完全按照模板，不自作主张修改。**
> 1. 初始化只许写 `Data Settings!H1`（周一日期，设一次）；G3 / I3 / B 列时间公式 /
>    C5 / G 列周概览公式等**全部保持模板原样**，一个字符都不改。
>    （周概览 G13 在腾讯文档里显示 `//////` 是模板自带公式在该渲染器的已知瑕疵，
>    Excel/WPS 正常，不为此改模板。）
> 2. 只允许填写每日 sheet 红框范围：**C 列内容区（C6 起）+ E 列状态区（E6 起）**；
>    B 列、G 列、SUN 页、Data Settings（除 H1）等其他位置一律不可写。

内容区：**C 列**（C6 起）写时段工作内容，**E 列**（E6 起）写完成状态（Notes / Remarks / Completion Status）。
B 列是时间（模板自带 B6~B38 共 33 个时段行），G 列是周概览（在 SUN 页汇总，日页不用管）。

> 🔒 **硬规则：B 列的小时时段行一个都不许删。**
> 模板自带的时段行是固排结构，**绝不裁剪、绝不清空任何一行**。下班之后的时段留白即可，
> 内容只往对应时段的 C 列填。

## 排班规则（完全跟随模板格点，写死在 config.json）

| 项 | 值 |
|---|---|
| 模板开始时间 | 9:00 AM（模板 G3，**不许改**；config `work_start` 必须与之一致） |
| 时段间隔 | 60 分钟（模板 I3，**不许改**） |
| 行时间语义 | **结束点模型**：行时间 = 该段工作的结束时刻（9:00 行 = 8:00~9:00 的工作，实际含 8:30 到岗后的半小时） |
| 可填时段 | 9:00 / 10:00 / 11:00 / 12:00 / 14:00 / 15:00 / 16:00 / **17:00**（共 8 个，对应 C6~C9 + C11~C14） |
| 午休 | 12:00~13:00，**标注在 1:00 PM 行（C10）** |
| 不填的行 | 6:00 PM（C15）及以后、B 列其他时段行：留白 |
| 大小周 | 周一至周五，大周周六上班（config 的 `big_week_monday` 填了基准才判断） |

初始化（`init_week.py`）只做两件事：写 `Data Settings!H1` 周一日期 + 各日页午休行写「午休」；
其余模板内容一字不动。

## 标准流程

### 第 0 步：收集当日工作素材（写日报前必做）

写日报**不是**只凭用户一句话，先凑齐素材池（用 Read 工具读，不是靠猜）：

1. **用户当前说的清单** —— 最高优先级，作为主干。
2. **跨 agent 上下文**：Read `D:/yefengwei/wkt/公共盘/日报/context/{date}.md`（没有就跳过）。
3. **git 扫描（必跑，无论有无提交）**：跑 scan_git（见第 2 步）。产出四类素材都要看：
   `commits`（当日提交，**全本地分支**，切过分支的也收）、`staged`/`unstaged`/`untracked`
   （**只收文件修改日期在近三天内的**，更早的自动排除并在 beyond_window 里给计数）、
   `recent_modified`（全树扫描近三天修改的代码文件，标注 git 状态与修改日期；
   `today_modified` 是其中当日子集——没提交没 add 的当天工作全靠它兜底）。
4. **当前 agent 的当日上下文**：
   - 本会话今天围绕 wkt 做的实质开发工作（回顾对话历史，**排除日报填写本身**）；
   - Read `D:/yefengwei/.workbuddy/memory/{date}.md`（工作区记忆日志）里**与 WKT 相关**的条目。
5. 若用户是在别的 agent 里干完活回来填日报，而那个 agent 没写 context → 主动问用户贴一下
   或让用户提供那条会话的记录，整理后补进 context 再分析。

> 🤖 **自动模式（用户没给清单时默认启用）**：用户只说「填日报」「记录一下今天的日报」
> 而没有给具体工作内容时，**不要追问**，直接按上面 2~4 自动收集素材（git 当日提交
> 全分支、近三天修改的暂存/工作区文件 + 全树近期修改文件兜底、agent 当日围绕 wkt
> 目录的上下文），汇总分配到 8 个时段填入，填完在回复里列出时段表供用户核对修改。
>
> 🤖 **今日素材少时：近三天扩充 + 换话术（用户 2026-09-04 明确）**：若当天素材不足以
> 铺满 8 个时段（比如只改了两三个文件、没提交），**把近三天（`recent_modified` 全集 +
> 三日内 commits）的工作量拿过来，用另一套话术再套一遍补进当天日报**：
> - 同一件事在**当天的 8 个时段内**本来就要换写（词库见第 3 步）——跨日扩充也一样，
>   但措辞角度要与**这一天日报里已写过的**明显不同（换动词 + 换视角：实现→验证→
>   优化→梳理……），读起来不能像复制粘贴；
> - 近三天素材要**按时间线重新组织**：不要写「昨天做了 X」，而是把 X 拆成当天视角的
>   延续动作（如「继续完善报价成本计算，核对其余费用场景」「复盘汇总接口边界，
>   修正空数据兜底」）；
> - 优先补与当天素材**同模块**的近三天工作（延续性自然），不同模块的放后半段；
> - 宁可合理覆盖（耗时长的任务占 2~3 个时段），不要编造不存在的工作。
>
> 🤖 **素材池为空时（同样重要）**：若近三天无提交、`recent_modified` 为空、context 无
> 软件开发条目、记忆日志也没有 WKT 相关产出 → **日报 C 列留白（只保留午休行），
> 绝不编造、也绝不把 agent 的工具搭建过程填进去**（2026-09-03 的教训），然后明确告知
> 用户"近期无软件开发素材，请补充实际工作内容"。日报空着比填错内容好。

> ⚠️ **过滤原则（用户 2026-09-03 强化）**：context 和日报只收**围绕 D:/yefengwei/wkt 的
> 软件开发工作**。agent 自身的工具搭建（含本 skill 的开发迭代）、环境维护、个人事务
> 一律不进。若发现 context 里混入了这类条目，提醒用户并可按其要求重置。

### 第 1 步：初始化本周工作簿

```bash
"$PY" scripts/init_week.py --date 2026-09-03 --force
```

- 自动算周一（2026-08-31），文件不存在就从模板复制并初始化，存在则就地刷新。
- **最小侵入**：只写 `Data Settings!H1`（周一日期）+ 各日页午休行写「午休」，
  模板其余部分一字不动。
- 文件名：`WKT-23028-Daily-Work-Schedule-2026-YefengWei-{周一日期}.xlsx`
  （日期格式 `YYYY-MM-DD`，Windows 文件名不含斜杠）
- 输出 JSON 里 `days.Thursday.rows` 给出「时间 → 单元格」映射，`work_slots` 是可填时段。

### 第 2 步：扫描当日 git 提交 + 近期修改文件（内容补充）

```bash
"$PY" scripts/scan_git.py --date 2026-09-03 --out <skill>/.tmp/scan.json
# 需要看具体改动时加 --with-diff --max-lines 60
```

- 扫 `D:/yefengwei/wkt` 下深度 3 内的所有 git 仓库（当前命中 9 个）。
- **提交按所有本地分支扫**（`git log --all`）：每个项目有多个本地分支（如 wkt 的
  master / 报价系统），人经常切来切去，只扫 HEAD 会漏掉切走分支前做的当日提交。
- **无论当天有没有提交，暂存/工作区/未跟踪文件都会被分析**，但只收
  **文件修改日期在近三天内**（目标日 + 前两天，`--mtime-days` 可调）的条目；
  更早的遗留改动不计入（`beyond_window` 给计数）。
- `recent_modified`：全树扫描修改日期在窗口内的代码文件（`--no-tree` 可关闭），标注
  git 状态（staged/unstaged/untracked/committed-or-clean）与修改日期、时间。
  `today_modified` 是其中「修改日期=目标日」的子集。
- 自动排除 `.md`、测试代码、构建产物、图片字体，以及 `auto-imports.d.ts` 等
  vite 插件自动生成的声明文件（一跑 dev 就刷新，不算工作量）。
- 只看别人的提交？加 `--all-authors`（默认只认 config 里的 `git_authors`）。
- 分析优先级：当天素材 = `commits` + `today_modified` + 当日 context；
  近三天素材 = `recent_modified` 全集（今日素材不够时扩充用）。

### 第 3 步：汇总并分配到 8 个时段（这一步靠你写，不是脚本）

规则：

1. **以用户给的清单为主干**；git 提交、context 文件、当前 agent 当日上下文为补充。
   - git 里有但用户没提的（补了个字段、改了个 DTO）要写进去 —— 这是「工作补充」的意义；
   - context 里其他 agent 记的活也要纳入 —— 这是跨 agent 汇总的意义；
   - 补充项若明显是同一件事的延续，与主干合并，不要硬凑成两条。
2. 按时间顺序铺满 8 个可填时段：**9:00 / 10:00 / 11:00 / 12:00 / 14:00 / 15:00 / 16:00 / 17:00**
   （结束点模型：10:00 行写 9:00~10:00 的工作……17:00 行写 16:00~17:00 的工作；
   1:00 PM 是午休行跳过、6:00 PM 起不填）。
3. **条目少于 8 条**：耗时长的任务占 2~3 个时段，每个时段换写法（见下）。
4. **条目多于 8 条**：同类合并成一句。
5. **单条控制在 27 个汉字以内**（C 列宽约 56 半角 ≈ 27 全角，行高固定不换行，E 列写了
   状态后超宽部分会被裁掉看不见）。
6. **语言默认中文**（config `language: "zh"`）：C 列中文叙述，E 列状态写「已完成」/
   「进行中」。用户明确要求才切英文。
7. 动词开头，不加主语，专业简洁；不要出现「我」。

中文换写词库（同一个工作在不同时段换说法）：

| 阶段 | 可选动词 |
|---|---|
| 开始 | 启动 / 开始 / 着手 / 搭建 / 初始化 |
| 继续 | 继续 / 推进 / 跟进 / 深入开展 |
| 实现 | 实现 / 开发 / 编写 / 新增 / 接入 |
| 修复 | 修复 / 解决 / 排查并修复 / 处理 |
| 验证 | 验证 / 测试 / 自测 / 联调 / 核对 |
| 调整 | 调整 / 优化 / 完善 / 微调 |
| 重构 | 重构 / 梳理 / 整理 / 规范化 |
| 收尾 | 收尾 / 完成 / 归纳整理 / 沉淀文档 |
| 提交 | 提交代码 / 提交并推送 / 合并代码 |
| 沟通 | 沟通 / 对齐 / 同步进展 / 对接 |

示例（同一件事的三个时段，均 ≤27 汉字，time 为时段结束点）：

- 09:00 `启动报价管理模块开发，解析包装运输设置的数据结构`
- 10:00 `继续推进报价包装规则，对齐Excel模板计算公式`
- 11:00 `修复报价导出发现的舍入误差，并用样例数据验证`

E 列状态统一写「已完成」（有未完成的写「进行中」）。

### 第 4 步：写入

把 slots 写成 JSON（用 Write 工具写到 `<skill>/.tmp/slots.json`）：

```json
{
  "slots": [
    {"time": "09:00", "text": "启动报价管理模块开发，解析包装运输设置的数据结构"},
    {"time": "10:00", "text": "继续推进报价包装规则，对齐Excel模板计算公式"}
  ],
  "status": "已完成"
}
```

注意 `time` 是**时段结束时刻**（10:00 = 9:00~10:00 的工作），13:00 是午休行、18:00 起是
下班后的行，脚本会自动拒写（skipped 里报 protected）。

```bash
"$PY" scripts/fill_day.py --date 2026-09-03 --data-file <skill>/.tmp/slots.json
```

- 午休行和下班后的行**默认保护**，不会被覆盖（真要写加 `--force`）。
- `--mode append` 追加而不是覆盖；`--preview` 只读打印当天已有内容；`--clear` 清空当天。

### 第 5 步：交付 + 收尾沉淀

1. 用 present_files 打开生成的 xlsx，回复里给一个时段表摘要（时间 → 内容）。
2. **沉淀**：若本次会话还做了写日报之外的新工作，或填日报过程中确认了若干当日事项，
   追加到当日 context（防漏、防下个 agent 不知道）：

```bash
"$PY" scripts/log_ctx.py --source workbuddy-main --msg "当天新增工作条目"
```

## 注意事项

- **⚠️ `.tmp/slots.json` 是共享临时文件，必须整体覆盖不能复用**：实测踩过——别的 agent 写过的
  英文 slots 残留在里面，下一轮误填进 Thursday 就成了"莫名其妙的英文信息"。
  每次写入前用 Write 工具**整体覆盖**，填完核对内容语言与 `config.language` 是否一致。
- **🔒 模板的小时时段行只填不删**：B6~B38 是模板固排结构，`fill_day.py` 只写 C/E 列，
  `init_week.py` 完全不碰 B 列。任何"把多余行删掉更清爽"的想法都不要执行——用户明确禁止。
- **⚠️ 腾讯文档预览会回写旧版本（踩过实坑）**：用户在腾讯文档里开着这个 xlsx 预览时，
  脚本改完磁盘文件，腾讯文档可能再把它内存里的旧版本写回磁盘，**修改被静默覆盖**
  （实测：17:24 清空的内容，17:38 被回写成 17:11 的旧版本）。所以：
  1. 写文件前如果发现内容跟预期不符（比如明明清过又有残留），先查文件 mtime 判断是否被回写；
  2. 每次写完必须提醒用户：**关闭腾讯文档预览，重新打开文件**才能看到最新内容。
- **🔒 最小侵入初始化**：`init_week.py` 只写 `Data Settings!H1` + 各日页午休行「午休」，
  其余模板内容（G3/I3/B 列/C5/G 列周概览）一律不动——用户 2026-09-03 明确要求"完全按照
  模板，不自作主张修改"。模板换版后只需核对 config 的 work_start/interval 与新模板 G3/I3
  一致即可。
- **周概览 G13 在腾讯文档显示 `//////`**：模板自带公式在该渲染器的已知瑕疵（Excel/WPS 正常）。
  曾改成静态日期值，用户要求完全按模板后已撤销，恢复模板原公式——**不要再动 G 列**。
- openpyxl 不计算公式，所以脚本按「上班时间 + 序号×间隔」自己推算每行时间，与 Excel 打开后的
  显示结果一致。**不要**用 `data_only=True` 去读时间列，读到的是 None。
- 保存后公式缓存值会清掉，Excel/WPS 打开时自动重算，属正常现象。
- `wkt-erp-vue3-old` 之类不在 `git_root` 下的项目，扫不到就在对话里让用户贴提交记录。
- context 文件在公共盘上，只记可进日报的工作内容，**不要**写密码、密钥等敏感信息。
